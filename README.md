## הרשאות Admin / Member

מכשיר שיוצר את המשפחה ("יצירת משפחה חדשה") הופך ל-**Admin**; מכשיר שמצטרף עם קוד הזמנה הופך ל-**Member**. הפירוט המלא ב-[`supabase/migrations/0003_family_admin_roles.sql`](./supabase/migrations/0003_family_admin_roles.sql) (עמודת `role`, `current_family_role()`, `is_family_admin()`) ו-[`supabase/migrations/0004_admin_permissions_and_member_deletion.sql`](./supabase/migrations/0004_admin_permissions_and_member_deletion.sql) (הרשאות על `schedule_rules` + מחיקת בן משפחה אטומית).

**Admin בלבד:**
- הוספה/מחיקה של בני משפחה (מסך משפחה).
- ניהול לוח הזמנים הקבוע: הוספה/עריכה/מחיקה/סידור מחדש של שעות טיול, שינוי סבב הרוטציה (מסך לוח זמנים).
- החלפת/יצירה מחדש של קוד ההזמנה (הגדרות ← שיתוף המשפחה).

**כל בן משפחה (כולל Member):** צפייה בלוח הזמנים, צפייה ברשימת בני המשפחה, צפייה בהיסטוריה, סימון טיול כבוצע, החלפות תור, ובפרט **הוספת טיול ספונטני** ("טיול שבוצע") — זו פעולת טיול רגילה ולא שינוי בתצורת המשפחה הקבועה, ולכן פתוחה לכולם.

חשוב: זו לא רק הסתרת כפתורים ב-UI. הוספה/עדכון/מחיקה של `schedule_rules`, הוספת בן משפחה, החלפת קוד ההזמנה, ומחיקת בן משפחה חסומים ב-RLS/RPC ל-Admin בלבד בצד השרת — קריאה ישירה ל-Supabase ממכשיר של Member תיחסם באותה הדרך בדיוק כמו מהאפליקציה. `schedule_entries` ו-`walks` (כולל טיולים ספונטניים) נשארים פתוחים לכל בן משפחה — זו פעילות יומיומית רגילה, לא קונפיגורציה משפחתית.

מחיקת בן משפחה (Admin בלבד) עוברת דרך פונקציית `admin_delete_family_member()` (SECURITY DEFINER, ב-0004) — פעולה אטומית אחת שמיישמת את שיבוץ הסבב שכבר מחושב ע"י `planUserRemoval` (`src/logic/familyManagement.ts`), ומוחקת את המשתמש, בלי להשאיר אפשרות ל-DB חצי-מעודכן. טיולים שכבר בוצעו (`status = 'done'`) לא נוגעים — ההיסטוריה נשמרת תמיד. הפונקציה בודקת בעצמה בצד השרת (לא סומכת על הלקוח) שהמשתמש הנמחק שייך לאותה משפחה של הקורא, ושהקורא הוא באמת Admin של המשפחה הזו.

מצב מקומי/דמו (בלי Supabase): מכשיר יחיד = המשפחה כולה, אין מסך הצטרפות ואין הבחנת Admin/Member — התפקיד תמיד `admin` (מוגדר ב-`authStore`), וכל הפעולות זמינות כרגיל.
