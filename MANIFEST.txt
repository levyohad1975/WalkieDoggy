-2.A WHY "NO CLAIMED PERSONA" IS NOT SYNONYMOUS WITH "BOOTSTRAP"
--------------------------------------------------------------------
current_family_role()/is_real_family_admin() (migration 0016, Part 0) each
resolve a device's role in two branches: (1) if the device currently holds
a claimed persona (real_current_profile_id() is not null), read THAT
persona's users.role; (2) otherwise, fall back to
family_auth_members.role — the device's own permanent membership row,
independent of any persona claim.

The PREVIOUS version of both functions gated branch (2) on nothing more
than "branch (1) didn't apply" — i.e. literally just `persona_id is null`.
That condition was intended to mean "this device has never claimed a
persona in this family yet — genuine pre-first-member bootstrap." But it is
ALSO true the instant a device that USED TO hold a claim LOSES it — e.g.
Device A holds Dad/Admin, Device B calls
claim_family_profile_with_pin('dad', pin) and legitimately transfers Dad's
claim to itself (the atomic swap fixed in the prior "narrow
security/database correction pass", itself correct and completely
UNCHANGED by this fix). The instant that transfer commits,
real_current_profile_id() on A is null again too — not because A never
claimed anything, but because A just lost what it had. The OLD fallback
could not tell these two situations apart, and re-granted A admin
authority straight from its stale family_auth_members.role row.

-2.B THE EXACT VULNERABILITY, AND HOW IT'S CLOSED
--------------------------------------------------------------------
Confirmed by direct SQL trace (not assumed) — the OLD is_real_family_admin():
    persona_id := real_current_profile_id();
    if persona_id is not null then
      return exists (select 1 from users where id = persona_id and family_id = target_family_id and role = 'admin' and removed_at is null);
    end if;
    return exists (select 1 from family_auth_members where auth_user_id = auth.uid() and family_id = target_family_id and role = 'admin');
Device A above: persona_id is null (A holds no claim) -> falls to the
SECOND exists() -> A's family_auth_members.role is still 'admin' (never
touched by the claim transfer, which only ever writes to `users`, never to
family_auth_members) -> returns TRUE. A direct RPC call from A (any
admin-only RPC — set_member_role(), admin_delete_family_member(),
enter_qa_sandbox(), regenerate_invite_code(), ...) would have been WRONGLY
authorized. This is a server-side hole, fully independent of whether A's
own client-side checkClaimStillValid() has run yet.

THE FIX: the fallback is now gated on a REAL, server-verifiable bootstrap
predicate instead of "persona_id is null" — reusing the EXACT SAME
predicate this migration's own bootstrap_first_member_role() trigger
already uses to decide "is this genuinely the first active member ever for
this family" (chosen specifically for consistency, per the coordinator's
instruction to reuse the real predicate used elsewhere in this schema):

    not exists (select 1 from users where family_id = <fam> and removed_at is null)

i.e. "this family currently has LITERALLY ZERO active (non-removed)
personas in existence." Both functions now check this explicitly before
ever consulting family_auth_members.role, and fail closed (return
null / false) the moment it's false — regardless of WHY the calling
device holds no claim (never claimed one, or lost one). See the exact
corrected SQL in current_family_role()/is_real_family_admin()'s own
extensively-updated doc comments in the migration file itself.

0.B REQUIREMENT 1 — THE NON-ATOMIC CLAIM-SWAP BUG: ROOT CAUSE AND FIX
====================================================================
EXACT ROOT CAUSE: claim_family_profile_with_pin() (migration 0016)
previously ran exactly one statement to perform a claim:
  update users set auth_user_id = auth.uid() where id = p_target_user_id ...
This NEVER first cleared auth.uid() from whatever OTHER users row it might
already occupy. users.auth_user_id carries a UNIQUE index
(users_auth_user_id_idx) — so a same-device persona switch (e.g. Dad's
device, still holding Dad's own claim, verifying Idan's PIN to switch to
Idan) could hit that unique constraint outright on the single UPDATE
(Postgres evaluates the constraint per-row as each row is written, and the
OLD row claiming that auth.uid() was never touched, so the NEW row's write
collides with it), or, in a version that split "release" and "claim" into
two separately-failable statements/RPC calls, could leave the device
claimed on NEITHER profile if the second step failed after the first
succeeded.

THE FIX (rewritten claim_family_profile_with_pin(), migrations/0016_*.sql —
see that function's own extensive doc comment for the full walkthrough):
one atomic transaction, in this exact order:
  1. `select ... for update` on the target row — validates existence,
     family membership, and active/claimable status against a LOCKED row,
     and serializes any concurrent claim attempt against the SAME target.
  2. Idempotency check: if the locked row's auth_user_id already equals
     auth.uid(), return immediately as a safe no-op — no PIN check needed,
     nothing written, nothing audit-logged twice (Requirement 1, step 8).
  3. PIN verified against the LOCKED row's pin_hash BEFORE any mutation —
     a mismatch raises here, before either UPDATE runs, so the caller's
     existing claim (whatever it is) is provably untouched (Requirement 1,
     the "wrong PIN leaves original claim unchanged" adversarial case).
  4. `perform set_config('app.trusted_write', 'on', true);` — required
     because auth_user_id is now a protected column (see 0.C below).
  5. RELEASE: `update users set auth_user_id = null where auth_user_id =
     auth.uid();` — clears whichever OTHER profile this device currently
     holds, if any. THIS is the actual fix: it happens first, inside the
     same transaction as the claim below.
  6. CLAIM: `update users set auth_user_id = auth.uid() where id =
     p_target_user_id and family_id = target_family and removed_at is
     null;` — the WHERE guard re-validates against write-time state
     (defense-in-depth alongside the row lock from step 1).
  7. `get diagnostics updated_count = row_count;` then `set_config(...,
     'off', ...)`; if updated_count = 0, `raise exception` — and because
     NOTHING in this function catches exceptions internally, this raise
     unwinds the WHOLE transaction, including step 5's release. The
     device's prior claim, if the operation fails at this final check, is
     restored exactly as it was — it is never left "claimed nowhere."
  8. On success: audit log, done. All of steps 4-7 run inside the ONE
     implicit transaction PostgREST wraps around this single RPC call — no
     internal BEGIN/EXCEPTION block, so Postgres's own transaction
     semantics (any raised exception rolls back everything since the
     transaction began) are the actual atomicity guarantee, exactly
     mirroring how the ORIGINAL (pre-this-pass) claim_family_profile()
     already relied on the same "raise = full rollback, no partial writes"
     property for its own TOCTOU-safe design.

A transfer FROM another device (B claiming a profile A currently holds):
covered automatically by the above — B's own step-5 release only ever
touches B's OWN row (WHERE auth_user_id = auth.uid(), i.e. B's auth.uid());
A's row is untouched by that statement. Step 6's claim UPDATE is what
actually revokes A: it overwrites the TARGET row's auth_user_id from A's
value to B's, and the instant that commits A no longer satisfies
`auth_user_id = auth.uid()` for that row — no separate revoke statement is
needed, matching the existing model's own established comment ("the UPDATE
that moves the column IS the revocation"), now proven atomic alongside the
release-of-B's-own-prior-claim in the very same transaction.

claim_family_profile() (the NON-PIN claim path, originally migration 0004)
was NOT touched functionally — its own existing TOCTOU-safe design (a
guarded UPDATE + row-count check) already correctly refuses to steal an
actively-claimed profile, so it never faced this specific bug (it can only
ever claim an UNCLAIMED profile or re-affirm your own). It WAS redefined in
this migration (`create or replace function`, this repo's own established
convention for correcting an earlier already-shipped migration from a later
one — see 0.C below) purely to add the same app.trusted_write wrap around
its existing auth_user_id UPDATE, made structurally necessary by the new
protected-column trigger — its logic is byte-for-byte identical to the
original, re-verified directly against schema.sql before writing (not
reconstructed from memory) specifically to avoid a mistake caught and
corrected during an earlier pass of this same engagement.

ADVERSARIAL TEST/SQL CASES AND OUTCOMES (full reasoning is captured as
comments directly in the migration, next to claim_family_profile_with_pin()
— summarized here):
  - Dad -> Idan, same device: Dad's row cleared first (step 5), then Idan's
    row claimed (step 6), in one transaction. No unique-constraint
    collision. PASS.
  - Idan -> Dad, same device: symmetric, same mechanism. PASS.
  - A (device 1) -> B (device 2) transfer: A's claim on the transferred
    profile is gone the instant B's claim commits (overwritten row);
    whatever ELSE A might separately hold is completely untouched (B's
    release only ever touches B's own row). PASS.
  - Wrong PIN: raises before step 4 is ever reached — zero writes attempted
    this call; caller's prior claim (if any) is bit-for-bit unchanged.
    PASS.
  - Concurrent claims on the SAME target: the `select ... for update` lock
    fully serializes them. If both present the CORRECT PIN (a legitimate
    scenario under this function's own PIN-based-transfer design — not
    "first come first served"), both succeed IN TURN, deterministically,
    last-committer-wins — this is intentional PIN-transfer semantics, not
    corruption: the resulting database state is fully consistent (exactly
    one device holds the target, exactly per each device's own prior claim
    correctly resolved elsewhere). If the target instead becomes
    ineligible between the first commit and the second's now-unblocked
    re-check (e.g. concurrently removed), the second's step-6 WHERE guard
    matches 0 rows and it raises a clean, specific error, rolling back that
    second call's own step-5 release too — no corrupted state, no
    "claimed nowhere." PASS.
  - Re-claiming a profile you already hold (idempotent same-profile
    switch): the step-2 check returns immediately, no error, no writes.
    Client-observable in a new authStore.test.ts test
    ("re-claiming the profile this device already holds succeeds as a
    no-op"). PASS.
  - Failure at any step rolls back fully: guaranteed by ordinary Postgres
    transaction semantics as described in point 7 above — no internal
    exception handler anywhere in this function catches and continues past
    a raise. PASS.

0.C REQUIREMENT 2 — users.role / users.pin_hash COLUMN-LEVEL LOCKDOWN
(THE CRITICAL FINDING OF THIS PASS)
====================================================================
THE GAP, proven not assumed: schema.sql's "update users (self or admin,
active profiles only)" RLS policy controls which ROWS an authenticated
client may UPDATE — self, or any row if admin — but says NOTHING about
which COLUMNS a permitted UPDATE's SET list may touch. Before this pass, an
ORDINARY MEMBER, editing their OWN row (which the policy freely allows —
it genuinely is their own profile), could issue a direct PostgREST call
like `update users set name = 'x', role = 'admin' where id = <self>` and it
would pass RLS cleanly. This has NOTHING to do with any RPC — it is a raw
client REST call straight at the table, and nothing previously stopped
role/pin_hash/auth_user_id from riding along in that SAME statement's SET
list alongside a legitimate field like name/avatar.

AUDIT PERFORMED (every grant/policy/trigger on public.users, before
choosing a fix): confirmed via direct read of schema.sql that this repo
defines NO blanket `grant ... to authenticated` statements anywhere — it
relies entirely on Supabase's default privilege model (the `authenticated`
role gets full table DML by default; RLS row policies are the only gate
that existed). Confirmed the ONLY existing RLS policy governing UPDATE on
users is the self-or-admin one quoted above, and it is a ROW policy with no
column awareness (Postgres RLS itself has no column-level concept — that is
exactly why this needed a SEPARATE mechanism).

THE FIX CHOSEN, AND WHY — TWO independent layers, chosen over either alone
for defense-in-depth:

  LAYER A (primary): Postgres column-level privileges.
    revoke update on public.users from authenticated;
    grant update (name, avatar, photo_url, color, reminders_enabled,
      removed_at) on public.users to authenticated;
    revoke insert on public.users from authenticated;
    grant insert (id, family_id, name, avatar, photo_url, color,
      reminders_enabled, removed_at) on public.users to authenticated;
  Chosen as primary because it is the correct, purpose-built Postgres
  mechanism for exactly this gap (row policy vs. column policy), enforced
  BEFORE RLS or any trigger even runs, and rejects the WHOLE statement (not
  a silent partial-apply) the moment ANY column in the SET list lacks
  privilege — even an unchanged value in a protected column fails the
  whole statement, which is the strict behavior wanted here.

  Column list verified against the ACTUAL client code (NOT guessed) before
  choosing it: src/data/supabaseRepository.ts's fromUser() — used by BOTH
  upsertUser()'s UPDATE and createUser()'s INSERT/upsert-fallback — builds
  exactly {id, family_id, name, avatar, photo_url, color,
  reminders_enabled, removed_at}, NEVER role/pin_hash/auth_user_id.
  updateUserReminderSetting() touches only {reminders_enabled}, already a
  subset. This is therefore a PRECISE, verified-safe match for existing
  client behavior — zero breakage, no call needed splitting, because the
  client never sent a protected column in the first place.

  LAYER B (defense-in-depth): enforce_users_protected_columns(), a NEW
  `before update` trigger on `users` using the SAME app.trusted_write GUC
  pattern already established by migration 0005's
  enforce_walk_write_authorization() for the `walks` table:
    if app.trusted_write = 'on' for this transaction -> allow.
    else: raise if NEW.role/pin_hash/auth_user_id is distinct from OLD.
  Rationale for keeping this SECOND layer even though Layer A alone would
  already close the gap: if a FUTURE change ever needs to grant broader
  column privileges for some other legitimate field, Layer A's protection
  could silently erode unless someone remembers to keep
  role/pin_hash/auth_user_id carved out by hand every time — Layer B is an
  independent backstop that does not depend on anyone remembering that.
  set_config(..., true) is transaction-local, so an exception mid-write
  rolls back the GUC flag together with everything else — no try/finally
  needed, matching 0005's own idiom exactly.

  EVERY RPC that legitimately writes one of these three columns was
  updated to wrap its protected UPDATE with app.trusted_write on/off:
  set_member_role() (role), set_profile_pin() (pin_hash, both branches),
  claim_family_profile_with_pin() (auth_user_id, rewritten this pass
  anyway — see 0.B), claim_family_profile() (auth_user_id, newly redefined
  this pass specifically because of this trigger), enter_qa_sandbox() and
  exit_qa_sandbox() (auth_user_id, both release AND re-claim writes).
  admin_delete_family_member() needed NO change — it only ever writes
  removed_at, outside this trigger's protected-column scope.

  SECURITY DEFINER FUNCTIONS UNAFFECTED BY LAYER A: every privileged RPC in
  this schema is SECURITY DEFINER — its internal statements run as the
  function's OWNER role, which always has full table privileges regardless
  of what `authenticated` is granted. Layer A's REVOKE/GRANT therefore only
  ever gates a DIRECT client REST call issued as `authenticated` — exactly
  the vector this closes, and it changes nothing about how any existing RPC
  behaves internally.

ADVERSARIAL PROOF, REQUIRED AND STATED EXPLICITLY (full reasoning captured
as comments in the migration directly under the new trigger definition):
  A. Member's direct UPDATE setting role='admin' on their OWN row -> DENIED
     at the privilege-check stage (Layer A: `authenticated` has no UPDATE
     privilege on `role` at all — rejected before RLS or any trigger runs)
     AND, redundantly, by Layer B (NEW.role <> OLD.role with
     app.trusted_write unset -> raises). PROVEN, not assumed.
  B. Member's direct UPDATE of ordinary editable fields (name, avatar,
     photo_url, color, reminders_enabled) on their own row -> STILL WORKS:
     Layer A explicitly grants these; RLS's existing self-branch still
     applies underneath; Layer B only inspects the three protected columns
     and returns NEW unchanged for everything else.
  C. Member's direct UPDATE of pin_hash on their own row -> DENIED, same
     two-layer reasoning as A.
  D. set_member_role() called by an authorized admin -> WORKS: SECURITY
     DEFINER bypasses Layer A entirely; app.trusted_write bypasses Layer B;
     the function's own PRE-EXISTING is_family_admin() check (unchanged by
     this pass) is what actually gates who may call it successfully.
  E. set_member_role() called by a non-admin member -> DENIED, exactly as
     before this pass (is_family_admin() raises before the UPDATE is ever
     reached) — Part 0.5 adds a SECOND layer of protection for the case
     where a caller bypasses the RPC and goes straight at the table; it
     does not change this existing authorization check at all.
  F. set_profile_pin() through its authorized path (self, or admin
     resetting a non-admin member's PIN) -> WORKS, same reasoning as D.

2. THE FINAL AUTHORIZATION MODEL
--------------------------------------------------------------------
Answers to the coordinator's explicit questions:
- Real authenticated identity = `auth.uid()` (this device's Supabase
  session) — unchanged, always was, never client-supplied.
- Persona = whichever `users` row has `auth_user_id = auth.uid()`
  (`real_current_profile_id()`), OR the impersonation target if one is
  active (`current_profile_id()`) — unchanged.
- Admin role = NOW `users.role` OF THE CURRENTLY CLAIMED PERSONA (new
  column, this pass) — falling back to `family_auth_members.role` for that
  device ONLY in the brief bootstrap window before ANY persona has ever
  been claimed on it (right after create_family()/join_family(), before
  "add your first family member" has run).
- `current_family_role()`, `is_real_family_admin()` (both persona-first /
  family_auth_members-fallback), `set_member_role()`, `admin_delete_
  family_member()`'s last-admin guard, and `admin_list_family_activity()`'s
  role column were all rewritten to read from `users.role` on the claimed
  persona. `is_family_admin()`'s impersonation-aware wrapper (0006) is
  UNCHANGED — it already correctly short-circuits to false during
  impersonation regardless of this rework.
- `claim_family_profile()`/`claim_family_profile_with_pin()` needed NO code
  change at all — they already only ever touch `users.auth_user_id`; the
  fix lives entirely in what `is_real_family_admin()`/`current_family_role()`
  now READ, which those claim functions' existing UPDATE now correctly
  feeds into.

WHY THIS SHAPE (not moving family_auth_members itself on a claim
transfer): (a) `users` already IS the row that travels with the persona
everywhere else (name, avatar, pin_hash, auth_user_id) — role belongs
alongside them; (b) family_auth_members.auth_user_id's UNIQUE-per-device
constraint is relied on by unrelated things (bootstrap, join_family()'s
re-join-keeps-admin logic, the QA sandbox mechanism) that are cleaner kept
independent of persona-level authorization; (c) it fixes a second,
independently pre-existing quirk for free — a role change used to be able
to become "orphaned" from a persona if it was later reclaimed by a
different device; anchoring role on `users.id` (which never changes
identity even as its claim moves) makes that impossible by construction.

3. DAD→IDAN LOSES ADMIN, IDAN→DAD GAINS IT ONLY AFTER VERIFICATION
--------------------------------------------------------------------
Dad→Idan: claim_family_profile_with_pin('idan', pin) succeeds ->
users.auth_user_id for Idan's row = Dad's auth.uid() ->
current_profile_id() resolves to Idan's users.id ->
is_real_family_admin() reads real_current_profile_id() -> Idan's users.id
-> users.role for that row = 'member' -> false. Every admin-only RPC
(set_member_role, admin_delete_family_member, admin_list_family_activity,
create_family_invite, begin_impersonation, qa_reset_data/qa_reset_full,
current_family_is_qa-gated actions) now rejects this session.
Idan→Dad (the SAME device or a different one, reclaiming with Dad's own
PIN): symmetric, and only possible because claim_family_profile_with_pin()
independently verified Dad's actual bcrypt pin_hash BEFORE moving
auth_user_id — there is no path to admin authority that bypasses that
verification. A wrong PIN raises 'incorrect PIN' BEFORE the UPDATE runs —
zero rows touched, zero role change.
Client-side: authStore's `__signInCore()` (shared by signIn()/
signInWithPin()) now calls `refreshFamilyRole()` after every successful
claim — without this, the CLIENT's cached familyRole would keep showing
the stale pre-claim value even though the server-side authorization had
already correctly changed. This was a real, separate gap this pass closed
(see authStore.ts's own doc comment on `__signInCore`).

5. PIN SECURITY
--------------------------------------------------------------------
- Storage: bcrypt hash only (pgcrypto crypt()/gen_salt('bf')), never
  plaintext, anywhere — verified this pass with a fresh grep across the
  whole client tree for any AsyncStorage/log write of a PIN value: none
  found. PinEntryModal.tsx/PinSetupModal.tsx hold the entered PIN only in
  local component state for as long as the modal is open.
- Verification: claim_family_profile_with_pin() compares via
  extensions.crypt(p_pin, target_pin_hash) server-side; a wrong PIN raises
  'incorrect PIN' before any row is touched.
- Change/reset authorization: set_profile_pin() — self always allowed; a
  family admin may reset a NON-admin member's PIN (locked-out recovery);
  an admin's own PIN can ONLY be set by that admin themselves — EXPLICIT
  PRODUCT CHOICE, stated per the coordinator's instruction: one admin
  resetting another admin's PIN is blocked outright, with no exception
  found anywhere in this codebase's existing product docs that would
  justify allowing it. The risk (silently reset -> reclaim -> act under
  the victim admin's name in the audit log) outweighs the convenience; the
  safe fallback is that admin resetting their own PIN, or a direct
  database/dashboard action by whoever holds the Supabase project's own
  credentials.
- Rate-limiting / brute-force exposure — DOCUMENTED, NOT IMPLEMENTED (per
  the coordinator's explicit instruction to state the constraint rather
  than silently skip it): claim_family_profile_with_pin() has no attempt
  counter, cooldown, or lockout. A 4-digit PIN has only 10,000
  possibilities; an already-authenticated member of the SAME family could
  script repeated attempts. A real deployment should add a per-target-
  profile attempt counter with an escalating cooldown/lockout (a new small
  table, checked before the bcrypt comparison) and/or Supabase-level rate
  limiting on this RPC specifically. Not implemented in this sandbox — no
  live database to tune thresholds against — but written up as a specific,
  concrete gap in the migration's own comment, not hand-waved.

8. QA ENTER/EXIT ARCHITECTURE (Deliverable 2, THE reversibility fix)
--------------------------------------------------------------------
THE BUG: the prior pass's create_qa_family() repointed the device's ONE
family_auth_members row (auth_user_id is its primary key — one family per
device, by design) at the new QA family with NO way back except rejoining
via invite code.
THE FIX: a new `family_membership_snapshots` table (RLS enabled, ZERO
policies — default-deny, same pattern as audit_log/impersonation_sessions
— touched only by the two RPCs below, only for auth.uid()'s own row).
`enter_qa_sandbox(p_family_name)`: if this device currently has a REAL
(non-QA) family_auth_members row, SNAPSHOTS its family_id/role/claimed-
persona into that table BEFORE switching (skips the snapshot if already
inside a QA context, so entering ANOTHER fresh QA family from within QA
never overwrites the true original). Releases the device's current persona
claim, then creates+switches into the new is_qa=true family, exactly like
create_family() does for a real one.
`exit_qa_sandbox()`: requires the device to currently be in a QA family;
restores family_auth_members.family_id/role from the snapshot, best-effort
re-claims the original persona (skips gracefully if it was since removed),
deletes the snapshot (one-shot restore), and returns the restored family.
Client: `authStore.setFamilyId()` (already the reused "store-reload
pattern" from real onboarding) now ALSO resyncs `currentUserId` from a
fresh `whoami()` call after every family switch — a new, necessary fix
this pass found: without it, the client's cached persona id from the
family just left would linger and could route into RootNavigator under a
stale identity. Result: enter/exit is fully automatic — no invite code, no
manual DB edit, no reinstall, no storage clear.
`create_qa_family()`/`qa_reset_family()` are KEPT as thin backward-compat
shims (delegating to enter_qa_sandbox()/qa_reset_data() respectively) so
any external caller of the old names is not broken and gets the FIXED
behavior automatically.
